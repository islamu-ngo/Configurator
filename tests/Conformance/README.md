# Recursive cross-client conformance

These first-party synthetic inputs specify observable configuration outcomes.
They contain no real application answers or private fixtures. Expected JSON is
written and reviewed independently; production composition must never regenerate
the expected values.

The explicit inventory is:

- `root-map.definition.json`: archive-retention choices with literal dynamic
  keys, ordinal case identity, typed integers and explicit null.
- `root-variant.definition.json`: workshop notifications selected between disk
  and queue branches, initialization, unapplied suggestions, nullable input and
  a deliberately synthetic secret.
- `synthetic-library.definition.json`: public library branch lending lists,
  boolean activation, integer loan periods, English/Arabic labels and a repeated
  output binding resolved within each branch row.
- `recursive-cases.json`: supplied values, explicit omission pointers, complete
  readiness, exact canonical complete bytes and exact draft bytes. A null
  expected output means composition must refuse, rather than emit a JSON null.

Consumers load these as explicit test resources in their existing owner projects.
Core covers validation/composition; interactive owners must additionally exercise
their real editing, import/document, correction and retirement seams. CLI tests
must invoke its entrypoint. Merely enumerating these cases or replaying Core
through a client wrapper does not establish client conformance.

The nineteen-case corpus covers value and scoped-output semantics and is not
the complete workstream acceptance suite. Its six consumers run alongside the
separate root mutation, import, correction, custody-race and locale owner
regressions. Published surfaces, actual hosts and assistive technology retain
their own qualification gates.
Definitions and outputs remain development contract `0.0.1`; family/revision
identity is independent. No expected result may be silently changed to match a
failing implementation.

The seven library vectors were specified before execution. An enabled branch
requires an integer period from 7, 14 or 28 days. A disabled branch neither
requires nor validates its period and contributes no output item. An enabled
14-day branch beside a disabled branch with an invalid period emits exactly
`{"loanDays":[14]}`. Two enabled branches with periods 7 and 28 emit
`{"loanDays":[7,28]}` in input order. A disabled branch without a period emits
`{"loanDays":[]}`. Missing active periods and string-valued active periods
refuse both complete and draft output. These public-only cases have identical
complete and draft bytes; translations change labels and direction, never
answers, input revision or artifact bytes.

An inactive first row with 7 days followed by an active row with 28 days emits
exactly `{"loanDays":[28]}`; filtering must not shift the item scope to the
inactive row. An active 21-day integer is outside the admitted choices and
refuses both complete and draft output, independently of JSON type validation.

Canonical document editing deliberately refuses newly supplied inactive values
with `document-value-inactive`, without changing answers or revision. The two
library cases containing inactive periods specify this separate import result
with `expectedDocumentCode`; their Core composition expectations remain intact.
The library output projection discards branch identity and has no inverse import
mapping. Browser library cases seed the rendered workspace's real Form owner,
then exercise rendered locale, readiness and deliberate complete/draft export.
The root-map and root-variant Browser cases retain real artifact import coverage.

This maintenance exercise adds one public definition and seven case rows, extends
the existing six owner consumers and adds one explicit resource per test project.
It requires no target exporter or production change. It does not qualify a new
host, prove assistive-technology behavior or complete contributor routing.
