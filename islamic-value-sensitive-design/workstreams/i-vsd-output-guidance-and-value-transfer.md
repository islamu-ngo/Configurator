## Executive Summary

The refined plan is **plan-aligned**. It gives operators useful follow-up guidance without inventing unfinished tasks, silently copying assertions between forms, or treating a browser download request as proof that a file was saved. It also separates a partial export from complete artifact coverage and requires a stale transfer review to be renewed before any answer is changed.

The ethical reasoning concerns choices the Configurator maintainers control. Accurate status supports Sidq, or truthful communication: operators should know what was actually exported and which answers it represents. Explicit review and protection of manual answers support their agency and stewardship of entrusted information. Effective sensitivity checks, masked controls, consent-gated secret access and synchronous retirement reduce foreseeable disclosure risks without adding telemetry or external data collection.

All five original pairs now have accepted local technical mitigation evidence.
Runtime failures preceded repairs, and current affected checks pass. Synthetic
Browser/native interaction supports bounded visible behavior, not stakeholder
understanding, full bidi, AT speech, religious certification or target acceptance.
No new material design or scholarly question blocks this bounded closure.

## Scope

The assessment covers authored next actions, transient per-workspace export history and staleness, inert scalar `suggestedFrom` links, explicit inline and transition adoption, Browser/Desktop/Terminal parity, public CLI definition inspection, bilingual presentation, and canonical example/store identity. It includes the provider's documentation and evidence claims because misleading claims can harm operators even when the underlying mechanism is local.

The following boundaries remain unchanged:

- Answers and prepared output stay local and transient in Browser. No localStorage/IndexedDB, answer-bearing requests, worker/cache payloads, telemetry or cross-definition tracking is introduced.
- Configurator prepares candidates. Target validation, authorization and apply remain with the target application. `legal-drafts` are drafts, not legal or scholarly approval.
- No automatic task redirect, reactive cross-form synchronization, hidden prefill, cross-session workflow persistence or generated-secret reuse.
- Every existing store release remains immutable, including revision 4 and any uncommitted release. User-owned strategy files remain outside this work.
- Core admits bounded data; Presentation owns interactive workflow state; native I/O stays outside Browser. CLI inspects public definition metadata through Core and does not acquire a Presentation dependency.

### IVSD-F001 - Completion and follow-up claims must describe the action actually observed

Lifecycle: **accepted** for local technical mitigation. Severity: **High**. Claim type: foreseeable design risk with verified local controls. Principles/domains: Sidq, Bayan and La Darar; design, technical, operations and evaluation. Stakeholders: single-task operators, multi-task operators and people relying on the exported configuration.

The original concern remains: an unconditional next-step banner can imply a duty where no companion task exists, while an exported badge can mislead an operator after the backing answers change. CTO-R2 adds two consequential distinctions. A successful Browser download interop call establishes a request, not receipt of a saved file; and one successful file in an option does not establish completion of its other artifacts.

Maintainers control the vocabulary, trigger and revision bound to those claims. R2 accepts captured preparation identity, exact artifact coverage, distinct delivery kinds and conservative global staleness. Any answer edit, including selector changes, makes prior evidence stale; view/locale changes do not. This may prompt re-export after navigation, but is preferable to an unsupported claim that an earlier task is still current. A proven successful action may enable guidance while coverage remains visibly partial.

Evidence: E01 sections 3, 5.5 and 7; E02 P1/P3/P5-P7; E04 Browser publication and native receipt seams. Validation level: design reasoning plus source traceability, not executed new behavior. Mitigation: **IVSD-M001**. Owners/next validation: Presentation and client implementers; P3.RED and adapter Red tests for S02/S04/S15/S17, with actual accessibility evidence before platform claims. No religious-legal escalation is implicated.

### IVSD-F002 - Reusing answers must preserve deliberate assertions and the exact review

Lifecycle: **accepted** for local technical mitigation. Severity: **High**. Claim type: foreseeable data-integrity and agency risk. Principles/domains: Sidq, Ihsan, Amanah and Rights of People; design, technical and governance. Stakeholders: operators and people whose organizational identity is represented in generated documents.

A bootstrap default and a standalone operator-identity document can legitimately differ. Treating matching names as equivalent facts can overwrite an intentional answer or spread an unreviewed organizational assertion. A review screen also loses meaning if its source or destination changes before confirmation and the tool silently applies newly read values.

Maintainers control whether linking is inert, how existing answers are selected, and whether confirmation applies what was reviewed. R2 retains shared projection `copy` for genuinely single facts and uses `suggestedFrom` only for independently editable data. Supplied values, explicit null/omission and invalid drafts are unchecked by default; `false` and `0` are valid present values. Ordinary editing or switching never copies answers. Transfer confirmation binds the exact form lifecycle/revision and candidate set, stages all changes, and adopts once with one undo entry or refuses without live mutation.

The inactive-source change was reassessed explicitly. Mutually exclusive task forms cannot both be active. A retained source may therefore be reused while its task is inactive only if it was actually supplied, remains individually valid, is not omitted or represented by an invalid draft, satisfies authored `when`, and is permitted by current custody. Destination applicability is evaluated in its real or isolated hypothetical context. This permits useful local reuse; it does not imply the source is current in the outside world or authorize another person's assertion. Source provenance and explicit adoption remain necessary, and copied targets stay editable.

Evidence: E01 sections 3/5.2-5.4; E02 P2/P4/P5-P7/P9; E05 accepted-state/revision/origin seams. Validation level: design validation with existing mechanism traceability. Mitigation: **IVSD-M002**. Owners/next validation: Presentation, definition authors and client implementers; P4.RED proves S05-S08/S16/S18-S19. Phase 9 must establish semantics for each of the seven provider field mappings rather than infer them from labels. No certification or assertion-veracity claim is supplied.

### IVSD-F003 - Effective sensitivity and current custody must govern every reuse path

Lifecycle: **accepted** for local technical mitigation. Severity: **Critical**. Claim type: foreseeable confidentiality and consent risk. Principles/domains: Amanah, Tajassus avoidance, La Darar and Rights of People; technical, design, operations and governance. Stakeholders: Browser users on shared devices, native operators and people represented by sensitive data.

A nominally public leaf can inherit protection from a parent or `writeOnly`. Checking only the leaf label can launder sensitive information into an unmasked target. A secret-bearing preview retained after consent revocation creates a separate disclosure path even if the visible answer control was cleared. Undo, held review objects and late callbacks must not restore retired data.

R2 compares maximum effective sensitivity along both paths, rejects all downgrades, excludes generated-secret endpoints and gates secret retrieval before it happens. Native custody and Browser secret-enabled custody do not grant permission to display protected values openly. Protected preview rows remain masked, while exported workflow records carry labels, presence and static coordinates rather than raw values or answer-holding closures.

Revoke, clear-private-state, workspace replacement and disposal synchronously retire reviews, export contexts, prepared output and applicable undo state, including the case where no currently present secret would otherwise cause a revision advance. This supports stewardship of entrusted information and minimizes unnecessary exposure. It does not promise physical zeroization of every managed string or control what a user does after an intentional export.

Evidence: E01 R07-R08, S09-S10/S15-S19 and sections 5/8; E02 P2-P7; E05 privacy/masking/undo seams and E06 custody rules. Validation level: design validation, no new exploit/runtime proof. Mitigation: **IVSD-M003**. Owners/next validation: Core admission, Presentation and client implementers; pre-fix P2.RED/P4.RED plus adapter race tests. A qualified authority is needed for any later legal/scholarly claim, not for applying these repository confidentiality constraints.

### IVSD-F004 - Bounded declarations must not become an unverified schema or execution engine

Lifecycle: **accepted** for local technical mitigation. Severity: **High**. Claim type: foreseeable reliability and interpretation risk. Principles/domains: La Darar, Sidq and Ihsan; technical, governance and evaluation. Stakeholders: definition authors, maintainers and operators.

The original graph concern is retained with a corrected distinction: data suggestion cycles must reject, but authored navigation may return to a stale task without automatically traversing any cycle. General regex or JSON Schema implication is unnecessary and would create a new, difficult-to-verify promise. `pattern` is unsupported in the current bounded contract; R2 does not introduce it.

Admission uses closed keys, static scalar endpoints, bounded predicates and a bounded indexed graph. Compatibility is proved only for admitted scalar relations, including finite enum/const values, nullability, enclosing numeric/string constraints and asserted formats; an unproven relation rejects. Runtime still validates the concrete transferred value and destination applicability. Existing markup/plain-text handling and thin renderers remain authoritative; no new executable expression, template expansion or HTML authority is granted by titles/descriptions.

The prior report's generic ReDoS wording is not evidence of a measured vulnerability. R2 addresses bounded work and explicit rejection rather than claiming a new regex engine is safe. Source/runtime admission, source locations, actual metadata construction and recomputed sorted capabilities must agree; a declared token alone does not establish support.

Evidence: E01 sections 2/5.1-5.2/11; E02 P1/P2/P8/P9; E07 Core contract and admission/compiler seams. Validation level: design validation and source traceability. Mitigation: **IVSD-M004**. Owners/next validation: Core/compiler/schema maintainers; runtime Red cases and native generator freshness checks. No new scholarly question arises.

### IVSD-F005 - Access, portability and support claims must include all promised clients

Lifecycle: **accepted** for local technical mitigation, with maintainers retaining the release/support gates below. Severity: **Medium-High**. Claim type: foreseeable exclusion and continuity risk. Principles/domains: Adl, Ihsan and Rights of People; strategy, design, technical, operations, governance and evaluation. Stakeholders: offline/native operators, Arabic readers, keyboard/assistive-technology users and maintainers.

Maintainers control whether guidance and deliberate reuse exist outside Browser, whether labels are localized, and whether users can retain reproducible public definition history. The existing Desktop directory chooser does not substitute for task selection. The planned CLI inspection route also does not yet exist; documenting it as present would be misleading.

R2 preserves first-class Desktop task selection separately from `SelectOutput`, Terminal keyboard workflow, and a real bounded read-only CLI command. Interactive clients share Presentation behavior; CLI reports public Core metadata without answers or authored free-text leakage. Each client phase includes en/ar and accessibility semantics, using the platform's actual APIs rather than claiming CSS behavior for native controls.

Every existing release is immutable, whether committed or not. A new canonical provider source advances family revision independently of the fixed public `0.0.1` contract version, and manually answered golden artifact bytes must remain unchanged. These choices support continuity without requiring obsolete adapters or compatibility readers. Package and headless checks cannot establish actual Browser, native-host or assistive-technology outcomes; those limits remain visible.

Evidence: E01 sections 2/6/10/12/14; E02 P5-P9; E04/E08 client and store observations. Validation level: design validation and source traceability. Mitigation: **IVSD-M005**. Owners/next validation: client, CLI, provider and packaging maintainers; named phase tests, immutable-history/golden checks and honest qualification records. No runtime accessibility or translation-quality Pass is claimed.

Rejected alternatives remain material to the decision:

- Automatic redirection or inferred “next tasks” would substitute provider guesses for operator choice and authored relevance.
- Reactive copying and default overwrites would conflate distinct assertions. Forcing every independent form into one shared field would also erase legitimate divergence.
- Requiring both branches active would make explicit inline reuse between mutually exclusive tasks unusable; reading any retained source without validity/condition/custody checks would be too broad.
- Re-reading changed sources at confirmation without renewed review would invalidate the operator's consent to the reviewed change.
- Treating the first successful file or a Browser request as “all saved” would overstate the observed outcome.
- General schema/regex subsumption, new persistence or a parallel answer cache would add responsibility without a required benefit.
- Rewriting an existing release, maintaining obsolete aliases, or excluding later clients/languages to simplify an early increment would violate retained scope or immutable identity.
