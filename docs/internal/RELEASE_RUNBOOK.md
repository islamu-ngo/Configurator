## Current procedure

Use [the release tool instructions](../../eng/release/README.md#collision-proof-change-workflow)
for atomic fragments, exact commit footers, complete-range provenance and
immutable commit-bound corrections. The integration branch is `main`; no release
history is created by the transfer. Empty release inputs are valid before the
first Configurator release.

The engine validates; it does not commit, tag, push, deploy or publish. Local
renderer acquisition and synthetic fixture selection are explained in the
[explicit test instructions](../../eng/release/README.md#tests). Passing them
is not authority to sign or publish.

### Immutable group corrections

Do not edit a committed fragment to repair incompatible group membership.
Use the [bounded group-correction record](../../eng/release/README.md#correct-immutable-group-membership)
to bind a replacement group to the original Change-Id and normalized-content
SHA-256. Only group compatibility uses the replacement; original release
entries, source snapshots, scopes, impacts and commit identities remain intact.
The replacement must still satisfy the one-scope group invariant.

Correction records are append-only release inputs. Stage validation rejects
mutation, deletion and renaming after commitment; preparation and range checks
reject uncommitted applicable records. Candidate and authorized-inventory
verification read the same records from the selected committed tree and include
them in source-document provenance. Corrections cannot repair secret-bearing or
otherwise invalid fragment content by hiding it.

## Future governed release flow

1. Review descriptor, summary and linked change fragments.
2. Prepare generated notes/context with a separately promoted Configurator bundle.
3. Review generated bytes and commit the final preparation commit `B`.
4. Verify the candidate at exact full `B`, never a mutable branch head.
5. Generate the tag message, sign outside the verifier, then verify the tag.
6. Verify stable `main` compare-and-swap/topology before an approved adapter acts.
7. Retain authoritative final evidence; transport metadata remains separate.

This describes retained capabilities and their required ordering, not an active
publication service. An adapter and real trust custody must be approved separately.

## Required controls before activation

### Preparation command

After `docs/internal/releases/<version>/release.yaml` and `summary.md` are
reviewed, run from the working tree at the intended range end. The end is the
checked-out `HEAD`; no branch name is derived from the line label.

```bash
dotnet run --project eng/release/src/Configurator.ReleaseEngineering/Configurator.ReleaseEngineering.csproj --configuration Release -- \
  prepare docs/internal/releases/<version>
```

The approved authority supplies:

```text
CONFIGURATOR_RELEASE_TRUSTED_BUNDLE
CONFIGURATOR_RELEASE_PROMOTION_RECEIPT
CONFIGURATOR_RELEASE_PROMOTION_SIGNATURE
CONFIGURATOR_RELEASE_PROMOTION_PRINCIPAL
CONFIGURATOR_RELEASE_MANIFEST_SHA256
CONFIGURATOR_RELEASE_BUNDLE_ID
CONFIGURATOR_RELEASE_BUNDLE_VERSION
CONFIGURATOR_RELEASE_POLICY_VERSION
CONFIGURATOR_RELEASE_CONFIG_VERSION
CONFIGURATOR_RELEASE_TRUST_VERSION
```

These are names, not credentials to embed in source. No Event values transfer.
Preparation verifies promotion before rendering, reads descriptor/summary,
derives the complete local range from `Previous-Published-Tag` to `HEAD`,
validates public fragments and impact evidence, atomically creates
`release-notes.md`, and writes authoritative `release-context.v1.json`.
Order is maintainer summary, release-visible details, then complete
provider-neutral commit range. Empty detail/impact sections are omitted.

It prints the exact `docs(release): prepare <version>` message with
`Changelog: skip` and `Changelog-Reason: release metadata commit`; it never
commits, tags, pushes, publishes, executes candidate code or uses the network.
Identical reruns are byte-idempotent. Differing generated files, path escape,
symlinks, range/context/fragment drift, renderer/write failure stop without
changing hand-authored descriptor or summary.

### Generated-note mismatch recovery

Promote updated engine and packaged template together; replacing a file inside
an accepted bundle is not promotion. Formatter changes can change authoritative
Markdown bytes even when governed context is identical.

Before committing `B`, preserve reviewed `release.yaml` and `summary.md`, remove
only that version's uncommitted generated `release-context.v1.json` and
`release-notes.md`, then rerun with the intended promoted bundle. Review the
complete regenerated pair. Do not bypass differing-file guards, edit notes by
hand or remove unrelated files. After signing, preserve historical bytes and
correct forward through a reviewed release correction/addendum.

Candidate verification at exact `B` rejects committed differences with
`candidate_release_notes_mismatch`; a clean worktree does not exempt notes.

### Categorized notes and formatter verification

Notes retain maintainer summary, categorized primary entries, applicable impact
evidence and complete technical range. Categories are Breaking Changes, Features,
Bug Fixes, Performance and Other Improvements, in that order; empty categories
are omitted. Breaking status precedes commit type: a breaking fix appears once
under Breaking Changes. Context order and release/backport identity are unchanged.
Evidence/complete-range references may repeat IDs without repeating primary entries.

Follow [explicit renderer checks](../../eng/release/README.md#tests) before
promoting a formatter change. The environment variable alone does not select
TUnit `[Explicit]` methods. Verify archive and executable against the lock,
retain upstream notices and run each exact selector with
`--minimum-expected-tests 1`.

Fixtures use real locked renderer bytes with synthetic receipts, SSH trust and
dummy engine bundle bytes. Passing is not signer/bootstrap approval. Applicable
configuration, security, breaking and operator impact evidence still belongs in
descriptor/fragments; category headings cannot replace it.

### Candidate verification command

After reviewed preparation commit `B`, verify that exact full commit object:

```bash
dotnet run --project eng/release/src/Configurator.ReleaseEngineering/Configurator.ReleaseEngineering.csproj --configuration Release -- \
  verify-candidate docs/internal/releases/<version> <full-B-oid>
```

No branch has to point at `B`. The verifier reads the same authority inputs as
`prepare`, validates local history without lazy fetches/replacement objects,
resolves base/previous annotated tags, requires linear descent and terminal `B`,
and requires `B`'s exact terminal skip footers. It recomputes context through
`B`, rerenders with the separate verified bundle, compares committed generated
artifacts byte-for-byte and writes/verifies `release-candidate.v1.json`.

Candidate evidence records full object anchors, version/line/date, range,
base/previous tags, integration old/new push preconditions, bundle/policy/config/
trust/tool hashes, and descriptor/fragment/summary/context/note hashes. It omits
branch refs/heads, tag object IDs, current time, provider metadata, identities,
emails, raw commit bodies, tokens and secrets.

```text
release_candidate_verified: docs/internal/releases/<version>/release-candidate.v1.json
verify_candidate_failed: candidate_committed_artifact_mismatch
verify_candidate_failed: candidate_object_anchors_moved
verify_candidate_failed: candidate_terminal_commit_not_release_metadata_skip
verify_candidate_failed: candidate_release_context_mismatch
verify_candidate_failed: candidate_release_notes_mismatch
verify_candidate_failed: candidate_manifest_stale
```

Tag recreation, squash/rebase/merge replacement, wrong parent/range, source or
bundle drift, shallow/partial/replace/graft state, object-format mismatch or
stale evidence stops before signing/publication.

### Tag message and final tag verification commands

After candidate success, generate the tag message from authoritative sources;
do not independently edit its narrative:

```bash
dotnet run --project eng/release/src/Configurator.ReleaseEngineering/Configurator.ReleaseEngineering.csproj --configuration Release -- \
  tag-message docs/internal/releases/<version> > /tmp/configurator-release-tag-message.txt
```

It contains only tag name, version, line, exact `B`, candidate SHA-256 and note
SHA-256, not an editable summary or final-manifest digest. An authorized operator
signs outside the verifier:

```bash
git -c gpg.format=ssh -c user.signingKey=/path/to/release-signing-key \
  tag -s v<version> <full-B-oid> -F /tmp/configurator-release-tag-message.txt
dotnet run --project eng/release/src/Configurator.ReleaseEngineering/Configurator.ReleaseEngineering.csproj --configuration Release -- \
  verify-tag docs/internal/releases/<version> v<version>
```

The public CLI accepts no caller-selected trust root/object override. It resolves
the full tag object, validates annotation/OpenSSH signature and authorized
role/principal/algorithm/date, exact name/target/line, candidate/source hashes and
byte-identical rerun evidence. It writes/verifies `release-evidence.v1.json`,
chained to candidate evidence by SHA-256.

```text
release_tag_verified: docs/internal/releases/<version>/release-evidence.v1.json
verify_tag_failed: release_tag_not_annotated
verify_tag_failed: release_tag_signature_invalid
verify_tag_failed: release_signer_unauthorized
verify_tag_failed: release_signer_revoked
verify_tag_failed: release_signer_not_current
verify_tag_failed: release_signer_algorithm_forbidden
verify_tag_failed: release_tag_wrong_target
verify_tag_failed: release_tag_name_mismatch
verify_tag_failed: release_tag_message_mismatch
verify_tag_failed: release_candidate_manifest_drift
verify_tag_failed: release_notes_hash_mismatch
verify_tag_failed: release_evidence_manifest_stale
```

Do not delete, recreate or move tags to repair failures. Preserve signed history,
correct forward and generate new governed evidence; discard only uncommitted
stale outputs when rerunning an unsigned candidate.

### Stable main verification command

After final tag verification, resolve local full old `origin/main` and tag object:

```bash
old_main_oid=$(git rev-parse --verify refs/remotes/origin/main^{commit})
tag_object_id=$(git rev-parse --verify refs/tags/v<version>^{object})
dotnet run --project eng/release/src/Configurator.ReleaseEngineering/Configurator.ReleaseEngineering.csproj --configuration Release -- \
  verify-main docs/internal/releases/<version> "$old_main_oid" "$tag_object_id"
```

The command reads only local objects/refs/final evidence. It never fetches,
pushes, signs, tags, commits, updates refs, executes candidate code or calls forge
APIs. Every successful stable action requires `origin/main` to still equal the
old OID. Newest moves require fast-forward descent to `B`; already-at-`B` is
idempotent. Older stable patches emit `no-main-move`; prereleases do not move main.

```text
release_main_verified: action=move-main old=<old-main-oid> new=<full-B-oid> tag=v<version> instruction=update-main-fast-forward
release_main_verified: action=already-at-target old=<full-B-oid> new=<full-B-oid> tag=v<version> instruction=no-op-main-already-at-release
release_main_verified: action=no-main-move old=<old-main-oid> new=<full-B-oid> tag=v<older-version> instruction=publish-release-without-main-update
verify_main_failed: release_main_oid_not_full
verify_main_failed: release_main_expected_old_missing
verify_main_failed: release_main_cas_mismatch
verify_main_failed: release_main_non_fast_forward
verify_main_failed: release_main_tag_object_mismatch
verify_main_failed: release_main_evidence_target_mismatch
verify_main_failed: release_main_prerelease_no_move
```

An approved adapter, not the verifier, performs protected compare-and-swap.
On failure discard the action and reverify current local candidate/tag/main
objects. `B`, candidate, tag target, committed notes and stable target are one
exact identity; branch heads are push preconditions only.

### Maintenance lines (open on demand, delete freely)

No branch is provisioned just because a release is tagged. Open a maintenance
line only for a real backport to an already-released stable line:

```bash
dotnet run --project eng/release/src/Configurator.ReleaseEngineering/Configurator.ReleaseEngineering.csproj --configuration Release -- \
  open-maintenance-line docs/internal/releases/<version> <full-tag-object-id>
```

It re-verifies the tag, rejects prereleases, derives
`refs/heads/release/<major>.<minor>` and prints an action. It never creates,
moves, deletes or force-updates refs. The only legal source is a verified signed
stable tag on that line, not `main` or an arbitrary commit. Existing branches
containing the release produce an `already-open` no-op. `refs/heads/v*` is
reserved for the version namespace.

Release verification remains possible after maintenance branches are removed
because it reads immutable tag, `B`, tree and base ancestry. Branch creation/
cleanup are separate authorized Git actions, not part of this documentation unit.

### Restricted security input

Embargo input stays outside public checkout, candidate bundle, context, notes,
manifests, checksums, diagnostics, logs and provider metadata. Use bounded codes,
never echo restricted paths, values, identities or exception text. After disclosure
authorization, only reviewed public disposition/advisory references cross into
generation. They must not alias restricted details, secrets, identities or paths
after Unicode/whitespace normalization.

The public marker gate distinguishes ordinary product descriptions, such as
restricted output or restricted writes, from reserved classification syntax and
restricted-detail/credential markers. It normalizes marker keys and scalar
values consistently. This is not a natural-language confidentiality classifier;
independent secret, embargo and Unicode checks remain required.

## Stop and recovery rules

- Stop on missing objects, shallow/partial history, replacement refs, bundle/
  policy mismatch, renderer drift, unauthorized/unsigned/replaced tags or moved
  push preconditions. Correct inputs or promote a new bundle; never bypass checks.
- If `B` changes after candidate verification, discard unsigned stale candidate
  evidence and return to generation/review. Never retarget a tag or force-push main.
- If embargo data appears publicly, stop publication, restrict artifact access
  where possible and preserve incident evidence without reproducing the value.
- If future provider transport fails after local verification, retain evidence
  and repair transport. An adapter must not regenerate/reinterpret the release.
- Keep historical signed bytes immutable and correct forward.

No Event provider evidence-generation, GitBook activation, trust bootstrap,
production receipts, secrets or deployment addresses are operating commands
here. The retained inert fixture path is the local real-renderer sequence in
[eng/release/README.md](../../eng/release/README.md#tests).
