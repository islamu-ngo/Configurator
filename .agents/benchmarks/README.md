# Cold-Start Benchmarks

> **Purpose**: Empirically verify that a zero-knowledge AI agent, entering this repo with no prior session memory, can produce a correct, architecture-compliant change using only the context system (`AGENTS.md` → intents → rules → skills → agents).
>
> **Hypothesis under test**: If the context system is well-designed, a cold-start agent should pass each benchmark scenario without human hand-holding.

## 2. How to Run a Benchmark

Benchmarks are **manual** today. A future enhancement may wire them into CI as an optional nightly job.

### Procedure (manual)

1. Open a **fresh agent session** (no prior conversation memory in this workspace).
2. Pick one scenario from [`cold-start-tasks.yaml`](cold-start-tasks.yaml).
3. Paste the scenario's `prompt` verbatim to the agent. Do **not** add hints.
4. Observe and record:
   - Did the agent correctly classify the intent? (`intent_id` match)
   - Did it read the documented `expected_must_reads`?
   - Did it make changes only inside `expected_paths_in_scope`?
   - Did it run the `expected_verification_commands`?
   - Does the final diff pass the scenario's `acceptance_criteria`?
   - First-turn input tokens, maximum live context, cumulative input/cache-read tokens, and tool-result bytes.
   - Duplicate unchanged bytes by content hash, full-file reads, full intent-registry reads, and scout result sizes.
5. Mark the scenario `PASS` / `FAIL` / `PARTIAL` in an explicitly authorized report under `.agents/benchmarks/reports/YYYY-MM-DD-<scenario-id>.md`. No report is generated by the YAML parser.

### Scoring

| Outcome | Meaning |
|---|---|
| `PASS` | All acceptance criteria met, correct intent classification, tests green, and every top-level `context_budget` limit satisfied. |
| `PARTIAL` | Correct result with one acceptance miss or one context-budget breach that did not affect correctness. |
| `FAIL` | Incorrect classification OR missed ≥ 2 acceptance criteria OR tests red. |

Target: at least 5 of 6 scenarios `PASS` on first attempt. If fewer than 5 pass,
the context system needs repair (see §4). No benchmark session was executed
merely by restoring or validating this file.

Context is product quality: prompt caching may reduce cost but does not satisfy a live-context or duplicate-content budget.

## 3. Scenarios (v1)

Six scenarios covering the actual Configurator contribution surfaces:

| ID | Intent Mapped | Acceptance Summary |
|---|---|---|
| `tooling-intake` | `repository-tooling` | Bounded single-document YAML command; native engineering tests only |
| `bounded-definition` | `definition-engine` | Value-safe oversized rejection, no partial preparation or sensitivity demotion |
| `protected-output` | `protected-artifacts` | Deterministic competing create-only writes; no overwrite/partial fallback |
| `public-launch` | `client-interface` | Registered pinned public metadata; no private browser input or arbitrary remote URL |
| `harness-parity` | `agent-context` | 17 physical twin pairs, target routing and actual harness discovery |
| `notices-transfer` | `provenance-docs` | Traceable first-party MIT authority and retained component terms; excluded corpus stays absent |

See [`cold-start-tasks.yaml`](cold-start-tasks.yaml) for the full scenario schema (prompt, expected intent, paths, tests, acceptance criteria).

### Schema and context budgets

Top-level fields are `version`, `last_updated`, `owner`, `context_budget` and
`scenarios`. Each scenario retains `id`, `intent_id`, `summary`, `prompt`,
`expected_must_reads`, `expected_paths_in_scope`, `expected_paths_forbidden`,
`expected_verification_commands`, `acceptance_criteria` and `notes`. The old
target shorthand (`benchmarks/request/expected_intent/required_reads/acceptance`)
is not the harness schema.

The original budgets are unchanged: 12,288 additional bootstrap bytes, 40,960
discovery-result bytes, 12,288 single-retrieval bytes, 1,500 scout-result
characters, zero duplicate unchanged bytes and zero full-registry reads.
Measure all metrics from §2; byte limits are not token limits.

Native YAML syntax verification uses the existing AgentWorkflow command:

```bash
dotnet eng/agent-workflow/src/Configurator.AgentWorkflow/bin/Release/net10.0/Configurator.AgentWorkflow.dll validate-intents .agents/benchmarks/cold-start-tasks.yaml
```

Its command name reflects the original consumer, but it validates bounded
UTF-8 single-document YAML only. Manually verify the fields/types above, six
unique IDs, referenced intent IDs, actual paths/commands and README parity.
Do not claim semantic schema validation from its `intents_yaml_valid` result.
If machine metadata/parser behavior changes, run only its owning engineering
tests per [PROJECTS.md](../../PROJECTS.md); prose-only context needs no .NET suite.

## 4. What to Do When a Benchmark Fails

A failing benchmark is a **signal**, not a bug. Triage in this order:

1. **Intent misclassification** → the agent picked the wrong intent from `intents.yaml` or no intent.
   - Fix: tighten `triggers` in the correct intent; add disambiguating keywords.
2. **Context overflow or duplication** → the agent loaded full registries/files, repeated unchanged context, or returned raw scout output.
   - Fix: improve intent routing, retrieve one heading/symbol, deduplicate by `path + heading/symbol + revision`, or tighten the scout output contract. Do not solve this by adding more must-reads.
3. **Missing evidence** → a concrete decision lacked required context.
   - Fix: add the smallest relevant heading or symbol to the intent/skill route; a whole-file must-read is the last resort.
4. **Out-of-scope edits** → the agent touched files outside the intent's `paths_in_scope`.
   - Fix: sharpen the intent's `paths_in_scope` and the scenario's `expected_paths_forbidden`.
5. **Skipped verification** → the agent did not run `expected_verification_commands`.
   - Fix: reinforce [AGENTS.md](../../AGENTS.md), [Operations](../../docs/internal/OPERATIONS.md) and the intent's `pr_checklist`.
6. **Architecture violation** → the agent produced code that breaks a rule in `docs/internal/QUICK_REFERENCE.md`.
   - Fix: promote the rule into the matching `.agents/rules/*.md` so it auto-loads when editing that path.

Record every failure in an authorized benchmark report (see §2); route recurring
findings to the target-owned process rather than a missing Event journal policy.

## 5. Refining Scenarios

The v1 scenarios are **synthetic**. Replace each with a **real closed issue or PR**
from Configurator that exercised the same surface. That will give the benchmarks
ecological validity; do not restore Event scenarios.

To propose a refinement:

1. Open the scenario YAML.
2. Replace the `prompt` with the original issue text (or an anonymized version).
3. Update `acceptance_criteria` to match the merged PR's diff scope.
4. If commits are authorized, include the scenario ID in the commit subject.
